# ジョブキューの設計

最初はジョブを単一プロセスのメモリ上に積んでいた。しばらく運用したところ、デプロイのたびに積んだジョブが消えることが分かった。そこで永続キューを挟む構成に切り替えた。切り替えの際にワーカーの起動順に依存する問題が出たので、起動シーケンスも作り直している。その後しばらくは安定していたが、決済のインシデントで滞留が起きた。

## キューのホーム

ジョブは投入されると「キューのホーム」に置かれ、ワーカーが順に引き取る — ここが処理の起点になる。ホームから出たジョブは、完了するまでどのワーカーが持っているかを追跡する。

## バックプレッシャの底

ワーカーの同時実行数には下限を設けている — これは底であって保証ではない。負荷が高い時はここまで絞られる。

## 失敗したジョブ

失敗したジョブはキューに再投入される。再投入の上限は設けていないため、恒久的に失敗するジョブは滞留の原因になる。

## 永続化方式の選択

当初は外部のメッセージブローカーを導入する案だったが、運用対象を増やさない判断でデータベースのテーブルを使う方式にした。スループット要件が上がった時は再検討する。
